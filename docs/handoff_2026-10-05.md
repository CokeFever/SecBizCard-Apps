## 這個 session 做了什麼 — magic word 模式重新設計

起點:1.6.2 build 185(magic word 首次面對一般使用者)實測踩到一個 critical bug —
設密語後自動 repack 失敗(紅字「Could not re-pack the backup: Magic word required
for this backup」),且密語看似沒存。往下追,發現整個「設密語 = 立即解密舊雲端檔 →
重打包 → 覆寫」的模式有設計缺陷,順勢重新設計。

### 核心原則(三動作徹底解耦)
核心不變量:**空資料永不覆寫雲端;restore 永不寫雲端;設密語永不碰 Drive。**

- **設密語** → `BackupService.setMagicWord(word)`:純本機儲存,無任何 Drive 操作
  (取代舊的 `setMagicWordAndRepack`)。UI 顯示「下次備份生效」,不觸發備份。
  → 直接消滅原 bug(不再去解一個可能解不開的舊雲端檔)。
- **備份** → `backup({force, allowEmpty})`:contacts 為空時擋下
  (`EmptyBackupFailure`),連 `force:true` 都繞不過;空資料不呼叫 `markBackedUp`。
  UI 層:本機無 contact 時 disable「Back Up Now」,引導先 Restore。
  備份前若雲端是 magicword 檔但本機無密語 → 提示「將移除密語保護」(讀 header,
  不解密)。
- **還原** → `restore({overrideMagicWord})`:只讀雲端;輸入的密語只用於本次解密、
  **不持久化**;成功後才詢問「要不要在這台裝置記住密語」。密語提示**三分狀態**
  (無 / 有但解不開 / 有且吻合)。確認文案明說「覆寫本機」+ 雲端比本機舊的反向警告。

### 文案
- `magicWordSaved` 等字串 5 語改成「下次備份生效」語意;移除過時的 repack 字串;
  新增 13 個安全防護相關字串(3 態提示、記住密語、降級警告、空資料引導、反向
  staleness 等)。
- `docs/release_1.6.2_store_copy.md` 無需改(原本就沒宣稱「設密語=立即上傳」)。

### 設計與決策的 source of truth
- `.agents/tasks/magic-word-model-redesign/design.md` — 13 個決策 + 完整情境模擬
  (A 設密語 / B 備份 / C 還原 / D 登出重裝 / E 競態 的矩陣與盲點處理)。
- `docs/web_portal_and_e2e_encryption_plan.md` 的「設定/變更 magic word 流程」段
