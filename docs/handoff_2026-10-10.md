## 🔐 後端保護 — App Check Stage 1(monitor-only,已就緒,**尚未 enforce**)

### 背景與策略(investigate 報告:`.agents/tasks/investigate-backend-protection/findings.md`)
SecBizCard-Apps 是 public repo。fork 者改 package name 仍指向 owner 的 Firebase 專案,**今天就能
用 owner 的後端**(所有 callable 只有 Firebase Auth 把關,證明不了「是哪個 app」)。對策 = Firebase
App Check(Play Integrity/App Attest),fork 改了 package name 就產不出有效 attestation。
- **兩類服務不同授權策略**:(1) **CV OCR(shared key 池)** → 只放行 owner 自家 app,企業走 BYOK
  自備 key(BYOK **完全不經過後端**,直打 Google Vision,所以在 recognizeCard 加 App Check
  **不會弄壞 BYOK**)。(2) **名片交換(handshake)** → 共用服務,未來企業可能要用 → 需 app-id
  **allowlist**(預設 owner only,可擴充給付費授權;Stage 2,先不做,先用模式 (a) 單專案)。
- owner app id(雙平台):`app.ixo.secbizcard`。owner admin UID:`3XGBn4cAy3h3RhNQ3rPuavGwjAu2`。

### ✅ 本次已代做(gcloud/REST,全 monitor-only,**線上零影響**)
- 啟用 `firebaseappcheck.googleapis.com` API。
- 註冊 Android **Play Integrity** provider(app `1:769422548283:android:27d1c89a4ca4b6c4eaab1e`)。
- 註冊 iOS **App Attest** provider(app `1:769422548283:ios:4e890df1eb8a72b4eaab1e`)。
- **所有 service 的 enforcement = OFF**(`/services` 清單為空)。= monitor 模式:後端照收所有請求,
  有沒有帶 App Check token 都放行。新版 app 上線後,Firebase Console → App Check 會開始出現
  attestation metrics 供觀察。

### ⚠️⚠️ 後端 enforce 的前置條件(未來要翻 enforce 前**必讀**,鐵律)
**在以下步驟全部完成前,絕對不要翻任何 enforce,否則打爆線上舊版使用者:**
```
1. 新版 app(1.6.4,含 App Check client)上架雙平台  ← 已啟動
2. 後端全程 monitor,不 enforce
3. 觀察 Firebase Console App Check metrics:verified 比例上升、舊版(無 App Check)流量下降
4. 雙平台「強制更新」把舊版使用者趕上來
5. 確認舊版幾乎歸零 → 才翻後端 enforce
```
翻 enforce 的實際動作(Stage 1,等步驟 5 後由 user 指示,另開 workflow):
- 後端 `functions/src/index.ts` 的 `recognizeCard` + `getOcrUsage` + `submitOcrFeedback` 的 onCall
  options 加 `enforceAppCheck: true`(+ 需要時檢查 `request.app`)。
- **這是改後端 code → 要走手動 `firebase_deploy.yml` 部署**(backend 手動部署慣例)。
- BYOK 不受影響(不經過後端)。

### Stage 2(未來,名片交換 + allowlist,先不做)
- handshake callables(createHandshakeSession/requestHandshake/respond/return)加 enforceAppCheck。
- 加 server-side app-id allowlist(Firestore `app_allowlist` 之類,預設 owner app only,可擴充付費授權)。
- ⚠️ 坑:app 目前**直接訂閱 Firestore handshake doc**(`.snapshots()`),所以 Firestore 本身也要開
  App Check,否則讀取路徑變繞過點 —— 而 Firestore App Check 影響 app **所有**直接讀 Firestore 的地方,
  牽連大,要分階段 monitor。
- 企業授權兩種信任模式:(a) 企業 app 掛 owner 的 Firebase 專案(簡單,租戶隔離弱)/ (b) 企業用自己
  專案 + per-licensee 憑證(乾淨隔離,符合計費歸企業,工程大)。**建議:Stage 2 先用 (a),但 allowlist
  檢查設計成之後能把 identity key 換成 (b) 而不改呼叫點。**

### Debug token(開發用,多數情況不需要)
App Check debug token 只在「後端 enforce 已開 + 想用模擬器測」時才需要;enforce 開了也通常用真機測
(真機有真 attestation,免 token)。要用時:本機 `fvm flutter run` 的 terminal log 會印
`Firebase App Check Debug Token: <UUID>` → 電腦瀏覽器開 Firebase Console → App Check → 該 app →
Manage debug tokens → 貼上。只影響開發機,與線上無關。現階段(monitor + fail-open)**完全不用管**。
